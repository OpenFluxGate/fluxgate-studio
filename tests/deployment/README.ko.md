# 1차 배포 안전성 개선

Python 3 및 PyYAML 6.0.3 환경에서 `python3 tests/deployment/test_workflows.py`를 실행한다.
테스트는 workflow 구조와 인라인 셸을 확인하며 sudo/curl/sleep/파일 작업을 모의 처리한다.
SSH·운영 서버·실제 systemd에는 접근하지 않는다. 통과는 실제 배포 성공을 뜻하지 않는다.

기준은 main 34b03a3c779680ec737c88d7d643e1e50efc107b다.
사전검사, 동일 checkout UI 품질 검사, 제한된 health 재시도, 실패 전파를 추가한다.
API/UI가 공통 concurrency 그룹을 쓰면 대기 작업 하나가 다른 구성요소를 취소할 수 있어
구성요소별 그룹을 사용한다. GitHub concurrency는 FIFO가 아니며 중간 대기 커밋은 교체될 수 있다.

## 남은 한계

- 업로드 전 중지 및 UI `.next` 삭제는 남아 있다. 원자적·무중단·자동 롤백 배포가 아니다.
  이 PR만으로 운영 준비가 완료됐다고 판단하면 안 된다.
- 사전검사는 기존 쓰기 가능한 배포 디렉터리와 loaded 서비스가 없으면 안전하게 실패한다.
- API/UI 독립 배포와 버전 간 호환성은 미검증이다.
- SSH 연결, 자격증명, 대상 호스트, 실행 사용자, ExecStart, 작업 경로, 권한,
  산출물 배치와 환경 파일은 미확인이다.
- 기존에 무시하던 UI 정적 파일 복사 실패가 실제 배치 문제를 드러낼 수 있다.
- HTTP health 성공만으로 DB 정합성이나 배포 SHA를 증명할 수 없다.
- 타임아웃/수동 취소는 여전히 배포를 중단시킬 수 있다. 자동 롤백은 없다.
- 이번 패치에서 UI 의존성 설치·전체 빌드, 실제 서버 검사, actionlint/shellcheck는
  실행하지 않았다. 전체 CI와 실제 서버 구성 검토가 필요하다.

2차에서는 systemd와 산출물 배치를 먼저 읽기 전용으로 확인한 뒤 후보 업로드,
이전 버전 보존, 전환 및 복원을 설계해야 한다. symlink 경로를 가정하거나
DB·정책 데이터를 자동으로 되돌리지 않는다. 여기에는 2차 스크립트를 연결하지 않았다.
