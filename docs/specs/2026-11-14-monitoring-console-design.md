# Studio 모니터링 콘솔 설계

- 작성일: 2026-11-14
- 상태: 검토 중
- 선행 작업: PR #3 (`feature/lts-0.5.0`, 0.5.0 정책 수명주기와 보안 강화). 구현은 #3이 `main`에 머지된 뒤 `main`에서 브랜치를 만들어 진행한다.

## 1. 배경과 목표

지금 Studio는 규칙 CRUD 화면 한 장뿐이다. 대시보드 지표도 규칙 개수만 센다. 서비스가 실제로 얼마나 허용하고 차단하는지는 Studio에서 볼 수 없다.

이번 작업으로 Studio를 운영자가 매일 여는 콘솔로 바꾼다.

1. 판정 이력을 바탕으로 한 실시간 모니터링: 허용·차단 추이, 상위 차단 키, 규칙 묶음별 마지막 판정 시각
2. 특정 키(회원 식별자 등)의 판정 이력 조회
3. 규칙 변경과 키 조회의 감사 기록
4. 사이드바 구조와 고밀도 스타일로 화면 전면 개편

## 2. 범위

포함한다.

- admin-api: 모니터링 API, 키 조회 API, 감사 기록 API, 현재 사용자 API
- UI: 개요, 규칙, 키 조회, 변경 기록 화면과 공통 레이아웃
- 판정 이력 컬렉션 조회용 인덱스와 Studio 자체 감사 기록 컬렉션

제외한다. 다음 단계에서 다룬다.

- 가정 미리보기: 규칙을 바꾸면 지난 이력 기준으로 차단이 몇 건이 되는지 재계산해서 보여 주는 기능
- 정책 게시(publish), 롤백 화면: #3의 API는 그대로 두고 화면은 다음 단계에서 붙인다.
- IP, API 키 기준 키 조회: 이번에는 `userId` 필드만 조회한다.
- 엔진 쪽 변경: 기본 이벤트 기록기에 `createdAt`과 TTL을 추가하는 일, APM 태그 같은 외부 모니터링 연동
- Redis 조회: Studio는 Redis의 버킷 상태를 읽지 않는다. 판정 이력만 쓴다.

## 3. 전제: PR #3에서 그대로 쓰는 것

| 항목 | #3의 구현 | 이번 설계에서 |

| 역할 | 읽기 `ROLE_USER`, 쓰기 `ROLE_ADMIN` (Keycloak `realm_access.roles`) | 화면 용어 viewer는 `ROLE_USER`, admin은 `ROLE_ADMIN`에 대응한다. 새 역할을 만들지 않는다. |
| 동시 수정 방지 | 규칙 버전 비교, 불일치 시 409 | 그대로 쓴다. 화면은 409를 "다른 사람이 먼저 바꿨습니다"로 보여 준다. |
| BFF 프록시 | 브라우저는 `/api/proxy/...`만 호출하고 토큰은 서버에만 둔다. 허용 경로 목록 `ALLOWED_PREFIXES` | 새 API 경로를 허용 목록에 추가한다. |
| 시뮬레이션 | `POST /api/rules/{id}/simulate` | 규칙 화면에서 그대로 쓴다. |
| 가져오기, 내보내기 | `GET /api/rules/export`, `POST /api/rules/import` | 규칙 화면에서 그대로 쓴다. |
| UI 테스트 | Vitest | 그대로 쓴다. |

## 4. 판정 이력 스키마

Studio는 서비스가 남긴 판정 이력을 읽기만 한다. 읽는 필드는 아래와 같다.

| 필드 | 형식 | 쓰임 |
|---|---|---|
| `timestamp` | long, epoch ms | 기간 조회의 기준. 기본 기록기와 사용자 정의 기록기 모두 이 필드를 남긴다. |
| `allowed` | boolean | 허용, 차단 구분 |
| `ruleSetId`, `ruleId`, `ruleName` | string | 묶음별, 규칙별 집계 |
| `userId` | string | 키 조회, 상위 차단 키 |
| `remainingTokens` | long | 키 조회의 남은 토큰 |
| `retryAfterMs` | long | 키 조회의 해제 예상 시각 |
| `endpoint`, `method` | string | 키 조회의 최근 판정 표 |

`createdAt`(Date)은 읽지 않는다. FluxGate 기본 기록기(`MongoRateLimitMetricsRecorder`)는 `createdAt`을 남기지 않기 때문이다. 보관 기간 관리는 서비스 쪽 책임으로 둔다.

## 5. 백엔드 (admin-api)

### 5.1 설정

```yaml
fluxgate:
  studio:
    monitoring:
      event-database: ${FLUXGATE_EVENT_DB:}          # 비우면 규칙 DB와 같은 DB
      event-collection: ${FLUXGATE_EVENT_COLLECTION:rate_limit_events}
      create-indexes: ${FLUXGATE_EVENT_CREATE_INDEXES:true}
      cache-ttl: 10s
      query-timeout: 5s                              # 집계 쿼리 maxTimeMS
      max-window: 24h                                # 모니터링 조회 상한
      key-lookup-max-window: 7d
      key-transforms: [none, sha256]                 # 키 조회 화면에 보일 변환 목록
    audit:
      collection: ${STUDIO_AUDIT_COLLECTION:studio_audit_log}
      retention: ${STUDIO_AUDIT_RETENTION:730d}      # 0이면 TTL 인덱스를 만들지 않음
```

### 5.2 API

모든 경로는 BFF 허용 목록에 추가한다. `api/monitoring`, `api/keys`, `api/audit`, `api/me`.

| 메서드, 경로 | 역할 | 내용 |
|---|---|---|
| `GET /api/me` | USER, ADMIN | 사용자 이름, 역할, `canWrite` |
| `GET /api/monitoring/overview?window=5m\|1h\|24h` | USER, ADMIN | 전체 판정 수, 차단 수, 차단율. 규칙 묶음별 판정 수, 차단 수, 차단율, 마지막 판정 시각, 미니 추이(기간을 12등분한 차단 수) |
| `GET /api/monitoring/timeseries?window=&ruleSetId=` | USER, ADMIN | 구간별 허용, 차단 건수. 5분은 10초, 1시간은 1분, 24시간은 15분 단위 |
| `GET /api/monitoring/top-rejected?window=&ruleSetId=&limit=20` | USER, ADMIN | 차단 판정을 `ruleSetId`, `userId`로 묶어 많은 순으로 돌려준다. `userId`가 없는 판정은 뺀다. `limit` 상한 100. USER에게는 키를 마스킹한다. |
| `GET /api/keys/transforms` | ADMIN | 설정된 변환 목록 |
| `POST /api/keys/decisions` | ADMIN | 본문 `{value, transform, window}`. 키 값이 URL과 접근 로그에 남지 않도록 POST로 받는다. |
| `GET /api/audit?action=&actor=&q=&from=&to=&page=&size=` | ADMIN | 감사 기록 목록 |

`window`는 정해진 값만 받는다. 상한을 넘거나 목록에 없는 값이면 400을 돌려준다.

### 5.3 집계

- 모든 집계는 `timestamp` 범위 조건을 첫 단계에 둔다.
- 추이는 `$group`에서 `timestamp`를 구간 길이로 내림한 값을 키로 쓴다. 판정이 없는 구간은 서버가 0으로 채워서 돌려준다.
- 개요의 규칙 묶음 목록은 등록된 규칙 묶음 전체를 기준으로 만든다. 판정이 없는 묶음도 0건으로 보여 준다. 마지막 판정 시각은 고른 기간과 관계없이 최근 24시간 안에서 찾고, 없으면 비워 둔다.
- 모든 집계에 `maxTimeMS`(기본 5초)를 건다.
- 같은 조건의 결과는 서버 메모리에 `cache-ttl`(기본 10초) 동안 둔다. 캐시 키는 경로와 파라미터다. 역할에 따른 마스킹은 캐시에서 꺼낸 뒤 응답 직전에 적용한다. 키 조회와 감사 기록은 캐시하지 않는다.

### 5.4 인덱스

`create-indexes`가 켜져 있으면 기동할 때 판정 이력 컬렉션에 아래 인덱스를 만든다. 이미 있으면 그대로 둔다. 권한이 없어서 실패하면 경고 로그만 남기고 기동을 계속한다. 공용 DB에서는 이 설정을 끄고 DB 담당자에게 생성을 요청한다.

- `{timestamp: 1}`: 전체 개요
- `{ruleSetId: 1, timestamp: 1}`: 묶음별 추이
- `{userId: 1, timestamp: -1}`: 키 조회

### 5.5 키 조회

1. 요청을 받으면 감사 기록(`KEY_LOOKUP`)을 먼저 저장한다. 저장에 실패하면 503을 돌려주고 조회하지 않는다.
2. `transform`이 `sha256`이면 입력값을 UTF-8 SHA-256 소문자 16진수로 바꿔 `userId`와 비교한다.
3. 기간 안의 판정을 규칙 묶음별로 나눠 아래를 돌려준다.
   - 마지막 판정 시각, 허용 여부, `remainingTokens`, `retryAfterMs`
   - 상태
     - `BLOCKED`: 마지막 판정이 차단이고, 지금이 `timestamp + retryAfterMs`보다 이르다.
     - `RECOVERED`: 마지막 판정이 차단이지만 해제 예상 시각이 지났다.
     - `ALLOWED`: 마지막 판정이 허용이다.
   - 기간 안의 허용, 차단 건수와 시간대별 건수
   - 최근 판정 100건
4. 화면에는 모든 상태를 "마지막 판정 기준"이라고 표시한다. Redis를 읽지 않으므로 지금 이 순간의 버킷 상태와 다를 수 있다.

### 5.6 감사 기록

컬렉션 `studio_audit_log`. 문서 하나의 모양은 아래와 같다.

```json
{
  "at": "2026-11-14T05:03:11Z",
  "actor": { "sub": "…", "username": "…", "name": "…" },
  "action": "RULE_UPDATE",
  "target": { "ruleSetId": "checkout-api", "ruleId": "checkout-api-per-user" },
  "before": { "bands": [{ "windowSeconds": 60, "capacity": 30 }] },
  "after":  { "bands": [{ "windowSeconds": 60, "capacity": 20 }] },
  "detail": {}
}
```

- 기록하는 동작은 다음과 같다.
  - 규칙: `RULE_CREATE`, `RULE_UPDATE`, `RULE_TOGGLE`, `RULE_DELETE`, `RULES_DELETE_ALL`, `RULES_IMPORT`
  - 정책: `POLICY_PUBLISH`, `POLICY_ROLLBACK`
  - 조회: `KEY_LOOKUP`
- `before`, `after`에는 바뀐 필드만 담는다.
- `KEY_LOOKUP`은 `detail`에 입력값, 변환, 기간을 담는다. 목록 화면에서는 입력값을 마스킹하고, 상세에서만 원문을 보여 준다.
- 규칙 변경의 기록은 변경이 끝난 뒤에 남긴다. 기록이 실패해도 변경은 되돌리지 않는다. 대신 ERROR 로그를 남기고, 응답 헤더 `X-Studio-Audit: failed`로 화면에 알린다.
- `retention`이 0보다 크면 `at`에 TTL 인덱스를 만든다.

### 5.7 마스킹

- 키가 4자 이하이면 `****`로 바꾼다.
- 그보다 길면 앞 2자와 뒤 2자만 남기고 가운데를 `****`로 바꾼다. 예: `123456789`는 `12****89`가 된다.

## 6. 화면 (ui-nextjs)

### 6.1 레이아웃과 스타일

- 왼쪽 사이드바에 메뉴를 둔다. 메뉴는 개요, 규칙, 키 조회, 변경 기록이다. 아래쪽에 사용자, 역할, 언어 전환, 라이트·다크 전환을 둔다.
- 스타일은 고밀도 데이터형이다.
  - 무채색 바탕에 상태 색은 두 가지만 쓴다. 빨강은 차단과 삭제된 값, 초록은 허용 상태와 추가된 값이다. 추이 그래프의 허용 막대는 차단이 눈에 띄도록 회색으로 둔다.
  - 숫자는 고정폭 글꼴로 쓴다.
  - 표 행 높이는 좁게 둔다.
- 색은 CSS 변수로 정의하고 라이트, 다크 두 벌을 둔다. 기본은 시스템 설정을 따른다. 기존 `ThemeContext`의 테마 3종과 그라데이션은 걷어낸다.
- 경로는 `/overview`, `/rules`, `/keys`, `/audit`이다. `/`는 `/overview`로 보낸다.
- `/api/me` 결과로 USER에게 키 조회, 변경 기록 메뉴와 수정 버튼을 숨긴다. 주소를 직접 입력해 들어오면 "권한 없음" 화면을 보여 준다.

### 6.2 개요

- 기간 선택: 5분, 1시간, 24시간
- 핵심 지표 5개: 판정, 차단, 차단율, 활성 규칙, 규칙 묶음. 앞의 3개는 모니터링 API에서, 뒤의 2개는 기존 `/api/dashboard/stats`에서 가져온다.
- 허용·차단 추이: 쌓은 막대그래프. 허용은 회색, 차단은 빨강
- 규칙 묶음 표: 묶음, 미니 추이, 판정 수, 차단율, 마지막 판정 시각
- 상위 차단 키 표: 키, 묶음, 차단 수, 마지막 차단 시각. ADMIN이 키를 누르면 키 조회 화면으로 간다.
- 외부 대시보드 링크: `NEXT_PUBLIC_EXTERNAL_DASHBOARD_URL`이 있으면 개요 상단에 링크를 보여 준다.

### 6.3 규칙

- 규칙 묶음별로 묶은 표를 보여 준다. 열은 규칙, 대상(scope), 한도, 실제 의미, 24시간 차단 수, 켜짐 여부다.
- 실제 의미 문장은 구간마다 "처음 C회 연속, 이후 T마다 1회"로 만든다. C는 용량이고, T는 구간 길이를 용량으로 나눈 값이다.
  - T가 정수 초면 그대로 쓴다. 예: `60s·30`은 "처음 30회 연속, 이후 2초마다 1회"가 된다.
  - T가 60의 배수면 분으로 쓴다. 예: `600s·5`는 "이후 2분마다 1회"가 된다.
  - 정수가 아니면 소수 첫째 자리까지 쓰고 "약"을 붙인다. 예: `60s·7`은 "이후 약 8.6초마다 1회"가 된다.
- 행을 고르면 오른쪽 패널에서 편집한다. 편집하는 동안 미리보기 문장을 바로 갱신한다.
- 저장 버튼을 누르면 확인 창을 띄운다. 확인 창에는 바뀐 값 비교와 함께 "저장하면 이 규칙 묶음을 쓰는 서비스에서 진행 중인 횟수가 초기화됩니다"라는 경고를 보여 준다.
- 시뮬레이션, 가져오기, 내보내기는 #3의 기능을 이 화면에 그대로 둔다.
- USER에게는 읽기 전용으로 보인다.

### 6.4 키 조회 (ADMIN)

- 입력은 변환 선택(`/api/keys/transforms`), 키 값, 기간(1시간, 24시간, 7일)이다.
- 결과는 세 부분이다.
  - 규칙 묶음별 상태 카드: 상태, 마지막 판정 시각, 해제 예상 시각 또는 남은 토큰, 기간 내 건수
  - 시간대별 막대
  - 최근 판정 표: 시각, 규칙, 요청, 판정, 남은 토큰, 다시 허용까지

### 6.5 변경 기록 (ADMIN)

- 동작, 사용자, 대상으로 걸러 본다. 페이지 단위로 넘긴다.
- 규칙 변경은 바뀐 값만 빨강과 초록으로 보여 준다. 키 조회는 마스킹한 입력값을 보여 준다.

### 6.6 데이터 갱신과 라이브러리

- SWR로 10초마다 다시 가져온다. 브라우저 탭이 보이지 않으면 멈춘다. 화면 위쪽에 "마지막 갱신 n초 전"을 표시한다.
- 추이 그래프는 Recharts로 그린다. 미니 추이는 SVG로 직접 그린다.
- 언어는 한국어와 영어를 사전 파일로 지원한다. 기본값은 `NEXT_PUBLIC_DEFAULT_LOCALE`(기본 `en`)으로 정하고, 사용자가 바꾼 값은 쿠키에 둔다.

## 7. 오류 처리

| 상황 | 동작 |
|---|---|
| 모니터링 조회 실패나 시간 초과 | 서버는 503을 돌려준다. 화면은 마지막으로 받은 데이터를 그대로 두고 "갱신 실패, 마지막 갱신 시각" 배너를 띄운다. 규칙 화면은 영향받지 않는다. |
| 판정 이력이 없음 | "판정 이력이 없습니다. 서비스의 이벤트 컬렉션 설정을 확인하세요."라고 안내한다. |
| 허용되지 않은 `window`, `limit` | 400. 화면은 선택지로만 보내므로 정상 사용에서는 생기지 않는다. |
| 규칙 동시 수정 | #3의 409를 받아 "다른 사람이 먼저 바꿨습니다. 새로 불러온 뒤 다시 수정하세요."를 보여 준다. |
| 키 조회의 감사 기록 실패 | 503, 조회하지 않는다. |
| 규칙 변경의 감사 기록 실패 | 변경은 유지한다. 응답 헤더를 보고 화면에 경고를 띄운다. |
| 인덱스 생성 실패 | 경고 로그만 남기고 기동한다. |
| 401 | 로그인 화면으로 보낸다. |
| 403 | "권한 없음" 화면을 보여 준다. |

## 8. 테스트

admin-api는 기존 Testcontainers Mongo를 쓴다.

- 판정 이력을 넣고 기간별 합계, 구간 나누기와 빈 구간 0 채우기, 차단율을 확인한다.
- 상위 차단 키의 정렬과 `limit`, 역할별 마스킹을 확인한다.
- 키 조회의 세 가지 상태, `sha256` 변환, 기간 상한을 확인한다.
- 권한: USER가 키 조회와 감사 기록을 호출하면 403인지 확인한다.
- 감사 기록
  - 저장소를 실패시켜 키 조회가 503으로 거부되는지 확인한다.
  - 규칙 변경이 유지되고 헤더가 붙는지 확인한다.
  - 변경 동작마다 `before`, `after`가 맞게 남는지 확인한다.
- 캐시: 10초 안의 같은 조회가 DB를 한 번만 부르는지 확인한다.
- 인덱스: 권한 실패를 흉내 내어 기동이 계속되는지 확인한다.

UI는 Vitest를 쓴다.

- 실제 의미 문장: 정수 초, 분 단위, 소수, 여러 구간
- 마스킹
- 변경 비교
- BFF 허용 목록에 새 경로가 들어갔는지, 다른 경로는 여전히 막히는지

CI의 lint, format, typecheck, test, build를 모두 통과해야 한다.

실환경 확인: 판정 이력이 쌓이는 개발 환경에 붙여 실제 데이터로 화면을 보고, USER 계정과 ADMIN 계정으로 각각 들어가 메뉴와 권한을 확인한다.
